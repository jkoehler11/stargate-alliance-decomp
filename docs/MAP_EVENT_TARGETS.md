# Which actor an event lands on, and whether that arms a sequence (PLAN 5.2)

`inventory/event_targets.csv` is one committed row per `.unr`, one per class that receives a fired event, one per
class that carries an `Actions` array, and a corpus census row. It is generated by `tools/event-targets.py`
(`make event-targets`), which reads each map's property blocks, resolves every fired name through the tag space, and
multiplies that by the `Actions` arrays the same map carries.

The two pages before this one measured the two edges of a level's graph and each stopped at its own edge.
`docs/MAP_ACTION_WIRING.md` says which sequence's `Actions` array names which placed action, and ends with the
warning that being named is not being run — *"the sequence must be activated, by a trigger, a `TriggerEvent`, or an
AI order"*. `docs/MAP_EVENT_WIRING.md` says which event name a placed actor fires and which name a sequence waits
on. Neither answers the question both defer to: **does the sequence holding those actions ever start?**

An event name in this engine is not a pointer. `TriggerEvent('X')` walks the level for actors whose `Tag` is `X` and
calls each one's `Trigger` event, so the name's real target is an actor, and the actor's class decides what being
triggered means. That gives the second hop this page measures:

* a fire site's name → the actors tagged with it (a **landing**) and their classes;
* a sequence that carries an `Actions` array → whether its own `Tag` is a name something fires (**armed**);
* every action those arrays wire → in an armed sequence, in a sequence whose tag is never fired, or in one that
  carries no tag at all.

A tag is not unique — many of them address more than one actor, and the artifact's `shared_tags` column counts
them — so landings are counted as pairs, not as names.
And a `ScriptedTrigger` is a touch volume as well as a sequence: it starts when a pawn walks into it, no name
involved, which is why the arming question only decides part of the population and the page says so rather than
reporting a percentage as a verdict.

Nothing game-derived is written: the CSV carries class names and counts, and this page quotes no event name.

A fired name resolves through `Tag`, not through a pointer: `TriggerEvent('X')` walks every actor tagged `X`, so the landing count is a count of pairs and 2205 tags address more than one actor. That is why the second column of this page is a **class** histogram -- what receives an event is the class of the actor that carries the tag.

**This is the chain 5.2 has been asking about, in one number.** `docs/MAP_ACTION_WIRING.md` says which sequence names which action; `docs/MAP_EVENT_WIRING.md` says which name a placed actor fires and which name a sequence waits on. Neither answers *does it run*: an action in a sequence that nothing starts is wired and still dead. Joining the sequence's own `Tag` to the fire population does, and 1374 of 16886 wired actions survive that join -- a placement is not a run, and being named by an array is not one either.

**The population is the classes', not one number's.** TeamScriptedSequence carries 1141 of the 2694 arrays and 8716 of the 16886 wired actions with 0 of them in a sequence a fire arms; ScriptedTrigger carries 1073 and 7065 with 1330 armed. The rest of the split is the finding: 15481 wired actions sit in a sequence whose tag nothing fires and 31 in one that carries no tag, so a name-based read decides the 1374 that are armed and sizes -- but does not settle -- the rest.

A `ScriptedTrigger` is a touch volume as well as a sequence -- a pawn walking into it starts the array with no name involved -- which is why the armed column is not a verdict on the classes that carry a volume. For the classes that are pure sequences the tag is the only handle a package gives, and there the fired-name count is the one that says whether anything in the level starts them.

## Reading a row

`kind=map` rows carry the per-map counts, `kind=target` rows how many fire-to-actor landings each class receives
(what a fired name lands on), and `kind=holder` rows how many sequences each class carries, how many actions their
arrays wire, and how many of those sit in a sequence whose tag a fire names. The corpus row is `kind=census` and
carries every total the prose quotes, so a re-render and a check read the same numbers.

The wired actions are split three ways and the split partitions them: `wired_armed` (the sequence's tag is a name
some placed actor fires), `wired_tag_unfired` (the sequence carries a tag and nothing fires it) and
`wired_untagged` (the sequence carries no tag, so no name could address it at all).

## Controls

* **the array census is the same one `docs/MAP_ACTION_WIRING.md` measured.** 2,694 arrays and 16,886 wired actions
  against that page's 2,694 arrays and 16,886 references to a placed action — the same numbers from a walk that
  reads the property block for a different reason, so the sequence side is not this page's own invention.
* **`kind=holder` is a class histogram, not a total.** Eight classes carry the arrays; the two that arm by name and
  the two volume classes that start on touch are counted apart, which is what keeps the headline from reading as a
  statement about every sequence.
* **landings are pairs.** `landing_classes` is the number of distinct receiving classes; a fire that lands on five
  actors tagged the same contributes five landings and one class, and `shared_tags` says how many tags are like that.

## What is not measured

* **A start that is not a name.** `TeamScriptedSequence` and `UnrealScriptedSequence` carry most of the wired actions
  in the corpus and none of them is armed by a fired tag, so their start is an AI order, a native call or a pointer
  a property block does not carry as a name. This page measures the population a name-based read decides; it does
  not claim the rest never runs.
* **Order and timing.** An armed sequence still runs its array in the array's order, and a landing says nothing
  about whether the fire happens before or after the sequence was armed.
* **The touch path.** A `ScriptedTrigger` that starts on contact needs no event name; modelling that would need the
  volume geometry, which `docs/T3D.md` writes but this walk does not read.
