# Which sequence runs which action (PLAN 5.2)

`inventory/action_wiring.csv` is one committed row per `.unr`, one per action class, one per class that carries an
`Actions` array, and a corpus census row. It is generated by `tools/action-wiring.py` (`make action-wiring`), which
reads each map's property blocks, decodes every `Actions` array, and resolves its elements against the same map's
export table.

`docs/MAP_SCRIPTS.md` settled what a level's logic is made of -- placed `ACTION_*` actors, not compiled script -- and
left two things open in its own words: *which sequence runs which action*, and *whether a placed action is reachable*
("an `ACTION_*` that no sequence references never runs, and nothing here distinguishes the two"). This page is that
read.

Every reference resolves inside its own map: the array holds 1-based export indices, so the wiring needs no name resolution and no cross-package join. `Actions` sits on 8 different classes, so the ordered lists are not a property of one actor class -- `ScriptedSequence` and its `ScriptedTrigger`/`TeamScriptedSequence` subclasses carry most of them, and the census row names how many holders are empty (a sequence that exists and runs nothing).

**`Actions` is two properties, not one.** 1472 of the 18379 references leave the scripted-action family and land on `MatAction` subclasses -- the scene manager's own `Actions` array, which orders a level's cutscene camera and animation steps. A join on the property name alone would read a camera move as a mission action. Both families are listed apart for that reason, and the holder table names which classes carry each.

## How an order is stored, and why it is one read

A sequence actor's `Actions` property is an `Array`, and in this build's property stream an array of objects is a
**count followed by that many compact indices** -- no names, no per-element type byte. Measured on `M00`'s
`ScriptedTrigger41`, the payload is `04 65 13 64 13 63 13 62 13`: four elements, each a two-byte compact index, and
the indices are consecutive (`1253, 1252, 1251, 1250`), which is a sequence placed as one block in the export table.

That is why the wiring needs no name resolution: the index is 1-based into the same package's export table, so an
element *is* the placed actor. The reader requires the decoded elements to consume the property's declared size
exactly, so a wrong guess about the element width fails visibly instead of silently reading a short list.

The control that this is the whole story is a scan in the other direction: across all 73 maps, **30 property values
that are not `Actions` name a placed action at all** -- and every one of the 30 is a mis-parsed block, not a
reference (the property names it reports are `Vector`, `CollisionRadius`, `StaticMeshActor299`). Nothing else in a
map package holds a pointer to an action, which is what makes the unwired count a statement about the map and not
about the reader.

## What this settles, and what it does not

**Settled.** The ordered list a sequence runs is a property value, and it is now resolved per map: an action either
appears in some sequence's `Actions` array or it runs nowhere, and the CSV carries both halves per map and per
class. `docs/MAP_SCRIPTS.md`'s "a placement is an upper bound on the logic a map can execute" is now a measured
bound rather than a warning.

**The family is the hierarchy's, not the name's.** `docs/MAP_SCRIPTS.md` counted carriers by the `ACTION_` prefix;
this walk reads `inventory/classes.csv`'s `super` chain and finds **`Action_PLAYANIM`** among the placements, a
concrete action whose class name the prefix cannot see (227 placements corpus-wide). That is a correction to the
carrier census, not a disagreement between two readers: the same `73 of 73` maps agree on the `ACTION_`-prefixed
subset, which the block above quotes.

**`Actions` is two different properties.** The scene manager carries an array of the same name whose elements are
`MatAction` subclasses -- camera moves, pauses, matinee waits -- so a join on the property name alone reads a
cutscene camera instruction as a mission action. The two families are counted apart, and only the scripted one is
turned into the wired/orphan count.

**Not measured.** Three things, all recorded rather than implied:

* **Which end of the order runs first.** The array is ordered, and the order is in the CSV only as a count per
  array. A per-element order is a T3D-level read (`docs/T3D.md` writes the array by size), not a census.
* **Whether a wired action is reachable in play.** Being named by a sequence is not being run: the *sequence* must
  be activated, by a trigger, a `TriggerEvent`, or an AI order. This page measures the inner edge of the graph;
  the outer edge is named events and is now measured in `docs/MAP_EVENT_WIRING.md`, which joins the `ExternalEvent`
  names a map's sequences wait on to the names its placed actors fire. What that page does not answer is a
  schedule -- it is the map's static name space, so a wait that nothing arms is still a wait the runtime could
  satisfy from a mechanism the package does not carry.
* **What the unwired actions are for.** An action no array names is either dead content, or reached by a mechanism
  outside `Actions` -- and the scan above says no property in the package points at one, so the first reading is
  the one the data supports.

## Reading a row

`kind=map` rows carry the per-map counts; `kind=action` rows carry placed / named / never-named / shared per action
class; `kind=holder` rows carry how many arrays each class carries, which is how the scene manager's participation
stays visible instead of being folded into a scripted-sequence total. `refs_none` counts empty slots in an order --
a `None` element is a real element, and 21 exist corpus-wide; `refs_dangling` and `refs_other` are non-zero only if
the reader is wrong somewhere, and both are zero.
