# Cut content report

Status: **first complete pass** (PLAN 3.4 / 5.6). Everything below is a claim about this Dec-2005
prototype, and each one carries the committed artifact it comes from — a CSV in `inventory/` or a doc
that measured it. The evidence standard that decided what belongs here comes first, because most of
the obvious "cut content" claims in a project like this are wrong.

## Why this is not a list of missing classes

The obvious shortcut is to diff the Dec-2005 packages against the Jun-2006 studio source and call
every class the leak lacks "cut". `docs/ORACLE_DIFF.md` shows why that is wrong: the leaked tree is
Perception's modified **Engine** source (269 `Engine` classes, 5 `Core`, 4 game classes) plus
`Pawn`/`ShadowProjector` as `.ucpp`, not a dump of the game's script packages. The 1,362
`build-only` classes are mostly classes the oracle never covered, so treating them as cut would
manufacture a finding out of a coverage gap.

## What does count

| evidence | source | strength |
|---|---|---|
| a mission in the campaign definition whose map is not in the dump | `inventory/chapters.csv` vs `inventory/maps.csv` | strong |
| recorded audio for a mission with no map | `inventory/music_index.csv`, `inventory/speech_index.csv` | strong |
| a map that no campaign entry and no menu flow reaches | `inventory/maps.csv`, `inventory/chapters.csv` | strong |
| a class placed only by multiplayer maps in a single-player prototype | `inventory/map_actors.csv` | strong for structure, silent on intent |
| a system present in the prototype but rewritten in the later source | `docs/ORACLE_DIFF.md` | medium — direction of work, not shipping intent |

A claim without a file, a count and a direction (present here, absent there) does not go in this
report.

## Findings, strongest first

### 1. Two campaign missions were cut with their music still in the build

`M01` and `M05` each have a full music group and no map:

- `M01` — 112 cues, 17.5 MiB (`inventory/music_index.csv`), and chapter 1 of `ChapterList.ini` names
  `m01a.unr`, which is not in the dump (`inventory/chapters.csv`).
- `M05` — 108 cues, 17.3 MiB, and **two** chapters (5 and 6: "Mission 5 Reetou Infiltration A/B")
  name `M05A.unr` and `M05B.unr`, neither present.

Neither has any recorded speech, so the missions were cut before dialogue was recorded — the music
was scored earlier than the voice work. That is a dateable difference inside the prototype, not an
inference about intent.

### 2. Music exists for a mission the campaign never mentions

`M11`: no map, no chapter, 140 cues inside the `M10_17` range group. This is the only id where the
audio is the *sole* remaining artifact — the campaign definition does not name it and no map ships,
so it can only be read from the audio group's label.

### 3. Four multiplayer maps were planned and not shipped

Chapters 34–37 name `SGCTF-HaakenVsTartarus.unr`, `SGCTF-KelownaVsRevanna.unr`,
`SL-SystemLordTestMapx.unr` and `CTF-Aztec.unr` — none present (`chapters.csv`, `present_on_disk`
false; `campaign_matrix.csv` lists them as the four chapters that name no mission id). The build
instead ships a different multiplayer set: `SGCTF-AbydosVsSGC`, `CTF-Abydos`, `CTF-LostCity` and 7
`DM-*` maps, none of which any chapter names.

### 4. The multiplayer maps are arenas, the missions are the game

Measured from `map_actors.csv`: the 10 multiplayer maps (`DM-*`, `CTF-*`, `SGCTF-*`) place **22
classes that appear in no mission map** (161 actors) — `HealthPickup` 41, `FragGrenadePickup` 25,
`TransportPlatform` 12, `SniperRiflePickup` 11, plus the shield/Zat/`C4`/`P90Torch` pickups and
`LinkedGate`. The 61 mission maps place **279 classes that never appear in a multiplayer map**
(31,574 actors), led by the single-player machinery: `PathNode` 8,568, `MovementMarker` 2,535,
`ACTION_SetAlertness` 1,404, `CoverInfo` 1,272, `ACTION_MoveToPoint` 1,254,
`TeamScriptedSequence` 1,244, `ACTION_SetViewTarget` 889, `IntelligentSpawner` 804.

So the DM/CTF maps in this single-player prototype are bare arenas with pickups — they carry none of
the AI scaffolding the missions are built from. They are shipped content, not cut content; what is
notable is that they exist at all in a build whose campaign does not start from the menu.

### 5. The campaign menu is pointed at the wrong map filenames

`System/tweak/Misc/ChapterList.ini` is the campaign definition (`StargateMenus.ChapterList.Chapters`
is `config(...)`), and its chapters name maps as `m02ax`, `m07axx`, `m17xa`, `m19x`, … while the dump
ships `M02A`, `M07A`, `M17A`, `M19A`, …. **Zero** chapters match a shipped filename literally; **30
of 37** match once the `x` build marker is stripped. A literal lookup by the menu therefore fails for
content that is present — which is exactly what the release notes describe: the campaign cannot be
started from the Single Player menu, and missions have to be loaded from **Continue**.

*Correction log:* the first draft of `docs/CONTENT_CENSUS.md` compared the sets literally and
reported "37 chapters, disjoint campaign". That was a normalisation bug, not a finding; the numbers
above are the corrected ones and `tools/content-census.py` strips the marker before matching.

### 6. 49 of the 73 shipped maps are referenced by nothing

Including `M00` — the map the release notes tell players to load from **Continue** — 7 `DM-*`, 2
`CTF-*`, `SGCTF-AbydosVsSGC`, `Entry` and `MainMenu` (`campaign_matrix.csv`, `CONTENT_CENSUS.md`).
Except the menu maps, these are reachable only by direct load or the Continue flow: a prototype whose
campaign glue was mid-rewrite while its content was complete.

### 7. Not cut content (recorded so nobody re-derives it)

13 classes exist in the Jun-2006 source and not in the build — the `SgPhys*` family
(`SgPhysActor`, `SgPhysCarParams`, `SgPhysPawn`, `SgPhysProp`, `SgPhysVehicleParams`), `GSInterface`,
`MovieMaterial`, `BspMeshActor`, `CameraOverlayRot`, `BaseProfileManager` and others. These are work
started **after** the prototype (`docs/ORACLE_DIFF.md` `oracle-only`), not content removed from it.
Likewise the 63 drifted + 11 divergent `Engine` classes are engine plumbing still being rewritten
(`docs/FORK.md` §5), not cut features.

## How much of the script tree the content reaches (`inventory/class_reach.csv`)

The findings above are about missions and audio. This is the same question asked from the other end — for
each of the 2,319 classes, is anything in the dump built out of it? Four independent signals, all committed:
placed in a `.unr` (`map_actors.csv`), present in a `.sgs` snapshot (`checkpoint_summary.csv`), a base class
of something reached (`classes.csv` supers), and named by a map's spawner (`squad_scripts.csv`).

| reach | classes | share |
|---|---:|---:|
| placed in a map | 381 | 16.4% |
| reached only through checkpoint state | 79 | 3.4% |
| a base class of something reached | 93 | 4.0% |
| **reached by content (any of the above)** | **553** | **23.8%** |
| referenced by nothing these artifacts can see | 1,766 | 76.2% |

Of the 381 placed classes, **359 appear only in mission maps and 22 only in multiplayer maps** (the DM/CTF
pickups and `LinkedGate` of finding 4), across **141,796 actor instances**. Three independent checks land on
numbers the system write-ups already published, which is what makes the artifact worth carrying:

* **no AI controller is placed in any map** — 25 controller/bot classes, 0 placements, which is
  `docs/systems/AI.md`'s finding arrived at from a different file;
* **vehicles are placed** — `StaffCannon` 21, `DeathGlider` 12, `Hummvee` 9, matching `VEHICLES.md`;
* **weapon classes are not** — 15 `StargateGame` weapon/ammo/damage classes, 1 placement, consistent with
  `WEAPONS.md`'s "no weapon is placed in any map".

The 79 checkpoint-only classes are the runtime spawns the checkpoint analysis predicted: `SVehicleTrigger`
1,115 instances, `InventoryAttachment` 288, `AttachmentP90Weap` 266, `Binoculars` 218.

**What "referenced by nothing" does not mean.** It is 76.2% of the tree, and calling that cut content would be
the same mistake finding 7 warns about. A class is invisible to these artifacts when it is reached only
through a *default property* — a pawn's `InventoryClasses`, a squad roster's members, an `AIScript` — and
defaults values are game data this repository does not publish (`docs/CLASS_DEFAULTS.md` reads them, but the
values stay in `$WORK`). Abstract bases, native shells and classes the engine names in C++ are the rest. What
the artifact does support is the opposite direction: **553 classes are provably reachable**, and any future
claim that a system is unused has to explain why its classes are not among them.

One negative worth recording: `squad_scripts.csv`'s 601 names match **no** class in the tree. They name
`.uc` AI scripts, not classes, so the spawner→roster link stays a defaults-level reference and cannot be
resolved from the map side.

## What would strengthen this

1. **Instance-level citations** — `make t3d` writes every map's actors to `$WORK` (73 files, 121,225 actors),
   but the *index* committed here is still class-level, so a claim can cite `SVehicleTrigger` 1,115 across the
   nine `.sgs` files and not "the fourth trigger in `M07A`". Committing an actor index would need the actor
   names, which are game data; the class-level reach census is what fits the rule.
2. **Map speech scenes to map scenes** (5.3 follow-up): the speech index has 14 mission ids and 34
   scene folders; the scene-to-quest mapping does not exist yet, so "recorded dialogue that no map
   can reach" is currently only provable at mission granularity.
3. **Runtime checks** (Phase 7): does the chapter list actually fail at load time as predicted, and
   can `M00` stand in for Mission 1? Predicted from static evidence; not observed.
