## What the 84.96% asset-export headline actually counts (measured 2026-11-22)

`docs/STATUS.md` reports **339 of 399 asset packages exported (84.96%)**. Read by directory, from
`inventory/assets.csv`, the shortfall is one class:

| directory | packages | exported | failed |
|---|---:|---:|---:|
| Animations | 82 | 81 | 1 |
| Sounds | 55 | 2 | 53 |
| StaticMeshes | 91 | 89 | 2 |
| Textures | 171 | 167 | 4 |
| **total** | **399** | **339** | **60** |

**53 of the 60 failures are `Sounds`, and umodel cannot read them by design** — every `.uax` leaves unread bytes
in `USound::Serialize` (the per-package errors are `Memory: bad allocation size`, not a parse the project could fix). Those
packages are not unexported: they go through this project's own reader, which indexes **1,364 speech WAVs and 1,923 music
WAVs** (PLAN 5.3). Counting them in the same fraction mixes two routes with two different tools.

Excluding that one class, **337 of 344 packages export — 97.97%** — and the real remainder is four
textures, two static meshes and one animation, of which `Goa_Vehicles` names its own cause (`wrong import index 31`). The
headline number is left as `status.py` generates it; this section says what is inside it, so the gap is not read as ten
times larger than it is.

## Sound is no longer a gap (measured 2026-11-26)

The coverage figure above excludes the sound packages because `umodel` cannot read them. That exclusion is now unnecessary:
a dedicated exporter reads all of them.

`umodel` treats a `Sound` payload as UE2's `Format` struct followed by a data array. These packages store a **complete RIFF
WAVE file** after a 13-byte prefix, which is why every one of them was refused. `tools/sound-export.py` finds the chunk and
writes it:

| | |
|---|---|
| `.uax` packages walked | **55** (54 carry `Sound` exports) |
| `Sound` exports | **3,047** |
| written as `.wav` | **3,047** — 93 MB, format tag 1 (PCM), mono, 8–11 kHz, 8/16 bit |
| failures | **0** |

`inventory/sound_export.csv` records each one: package, sound, export index, payload size, where the chunk starts, its
length and the six header fields.

**The census after that.** `inventory/assets.csv` holds 399 packages and 60 failures; 53 of those are the sound packages above,
leaving **7**:

| package | why |
|---|---|
| `M07_fresco_tex`, `M10_train_tex`, `Tutorial_Tex` | `assertion failed: Colors.Num() == 256` — paletted textures |
| `StargateGameFontsTex`, `Tutorial_Meshes` | `UTexture'…'.Palette: Property read error: 3` |
| `M10Meshes` | `Unknown class "Model"` |
| `Goa_Vehicles` | `Unknown class "MeshAnimation"` |

So **392 of 399 packages export** (339 by `umodel`, 53 by the sound exporter) and the 7 that remain are those above: four
paletted textures, two mesh packages and one animation class — the same four/two/one this page already described, with the
sound class no longer counted among them.

**The lesson, stated where the number lives**: 53 packages and 3,047 sounds were carried as "unreadable" for as long as an
exporter's limitation was recorded as a property of the data. *"Our tool cannot read it"* and *"it cannot be read"* are
different claims, and only the second belongs in a census.

### The four paletted textures: a starting point, not a mystery

`umodel` reports `Colors.Num() == 256` and `Palette: Property read error: 3` on the four texture packages. Two measurements
narrow what a reader has to do, and neither is what the error suggests:

| package | exports |
|---|---|
| `M07_fresco_tex` | 26 — **13 `Palette`** and 13 `Texture` |
| `Tutorial_Tex` | 24 — **12 `Palette`** and 12 `Texture` |

**The palette is its own export object**, one per texture, not an array inside the texture's payload. So the failure is not a
palette that is too small; it is the reader not resolving a reference to a sibling object.

**The texture payload is a tagged property block.** The first bytes of `M07_goldref` are

```
09 25 07 05 2a 03 00 02 04 3f 01 22 9abd474a 01 a2 00 e2 71 b8 40 0b 01 05 02 01 07 06 01 07 07 22 00 01 00 00 08 22
```

and `Tutorial_Tex`'s `Tut_ultrasound_01` starts `09 25 06 05 2a 03 2a 2e 2f 3f …` — the same shape: a tag stream with
compact name indices, then a struct-typed value (`3f`), then floats (`9abd474a` = the dword whose float reading is plausible
for a size) and a repeated `22 … 01 … 08 22` tail that looks like two more tags.

`Property read error: 3` is the reader failing on the **third** tag, so its tag grammar is wrong for this build rather than the
data being malformed — the same class of mistake as the sound packages, one layer down.

**What a reader must do**, and it is a bounded job: walk the tag block to its `None`, take the palette object reference, read
that sibling `Palette` export (its payload should be 256 × BGRA), then follow the mip descriptions to the pixel data. The
acceptance test is concrete: four packages, each producing one PNG per texture, with the palette applied.

#### The block already reads — `tools/prop-stream.py` is the reader

The suspicion above was that the tag grammar is wrong. It is not: the repo's own reader parses these payloads without
complaint.

```
Texture #14   1 property, 65604 trailing bytes   Palette -> Object Palette'Palette3'
blocks terminated cleanly: 1 of 1
```

One tag, a reference to a **sibling object**, and then 65,604 bytes of class-specific data. So a texture reader needs no new
tag grammar at all — only the class data after the block.

**The palette objects themselves** (`M07_fresco_tex` holds 13, all the same shape):

| | |
|---|---|
| payload | **4,099 bytes**, every one of the 13 |
| shape | 4,096 bytes of palette plus a 3-byte tag block (`None`) |
| first entries | `00 40 10 00 00 00 ff 00 00 00 ff 00 …` for `Palette54`, `00 40 10 00 7d 81 ff 00 04 08 ff 00 …` for `Palette53` |

**The layout is measured, not assumed.** Of the four possible byte offsets for a 4-byte entry, only one is consistent with a
colour format:

| entry offset | entries | byte 3 == 255 | byte 0 == 255 |
|---|---|---|---|
| 0 | 1,024 | 0 | 7 |
| 1 | 1,024 | 7 | 9 |
| 2 | 1,024 | 9 | 1,023 |
| **3** | **1,024** | **1,024** | 0 |

At offset 3 **every** entry ends in `ff`, which is an alpha channel and not a coincidence — so the palette body is
**1,024 entries of BGRA starting at byte 3**, and the three bytes before it are the tag block. The entries decode sensibly:
`00 7d 81 ff` is B=0, G=0x7d, R=0x81, A=255.

The 1,024 are **not** four copies of 256 — the quarters differ — and most are black (`00 00 00 ff`), with colour concentrated
early. Whether a P8 texture indexes the first 256 of them or the array is genuinely 1,024 wide is the one question left, and
it is answered by decoding one texture and looking at the result rather than by reading the layout. The acceptance test is
unchanged: four packages, one PNG per texture, palette applied.

#### The class data after the block: what is measured, and where it stops

`tools/prop-stream.py` parses the property block of every texture in the package, so the boundary between the block and the
class data is known exactly — and it moves:

| texture | size | properties | block ends | class data | its first bytes |
|---|---|---|---|---|---|
| `M07_goldref` | 65,611 | 1 | **7** | 65,604 | `02 04 3f 01 22 9a bd 47 4a 01 a2 00 e2 71 b8 40` |
| `M07_fresco_01` | 131,147 | 4 | **19** | 131,128 | `05 a8 cb 40 0b 01 05 02 01 08 06 01 07 07 22 00` |
| `M07_floorplate` | 262,219 | 11 | **57** | 262,162 | `01 f4 d3 07 00 40 80 20 52 69 74 ff 59 72 7c ff` |
| `M07_fx_symbol_03` | 16,459 | 8 | **57** | 16,402 | `01 3f 14 08 00 40 80 02 00 00 00 ff 00 00 00 ff` |
| `M07_fx_symbol_05` | 16,459 | 12 | **57** | 16,402 | `01 8a 54 08 00 40 80 02 00 00 00 ff 00 00 00 ff` |

**Three of the five** begin `01` then a four-byte value then `40 80`, and in those the bytes after that look like colour
(`… ff 00 00 00 ff`). Two do not: `M07_goldref` starts `02 04 3f 01 22` and `M07_fresco_01` starts `05 a8 cb 40 0b`.

**What that means, stated plainly**: the class data is *not* one fixed header followed by pixels. Either the leading bytes
describe a mip chain whose shape depends on the properties above them, or two of these five are a different storage variant.
Deciding which needs the same treatment that settled the sound packages and the palette: pick the hypothesis that predicts a
number, and check it across all 13 textures in both packages rather than the first five.

**Do not guess the layout into the reader.** The two failure modes are a 65,604-byte texture that is one flat P8 image and one
that is a mip chain with a header; a reader written against the wrong one produces plausible-looking noise, which is the kind
of error this page has spent the session learning to avoid. The next measurement is a table like the one above for all 13 × 2
textures, with the candidate fields decoded under each hypothesis, and the hypothesis that survives is the one where every
row's numbers agree with its payload size.

#### The textures decode — layout measured, output checked by eye

The layout is settled, and the test that settled it is arithmetic plus a channel check rather than an opinion:

| claim | evidence |
|---|---|
| data starts **16** bytes past the property block | at 16, byte 3 == 255 in **20,000 of 20,000** sampled pixels; at 17, 18 and 19 the alpha lands in the wrong byte (0 of 20,000) |
| size is `USize * VSize * 4` | true for every texture in `Tutorial_Tex` and `M07_fresco_tex` that states all three properties |
| pixels are **BGRA** | byte 3 is `ff` in every sampled pixel at the right offset |

`tools/texture-export.py` applies that: read the block with `prop-stream.py`, take `USize`/`VSize`/`Format` from the
properties, and for `Format == 5` write `USize * VSize * 4` bytes of BGRA at `+16` as a PNG.

**The run**: 170 `.utx` packages scanned, **49 PNGs** written (7.0 MB), 4,363 exports skipped — those whose properties do not
state `USize`/`VSize`/`Format`, where this tool would have to guess and therefore does not.

**The check that matters**: `Tutorial_Tex/Tut_signs_01.png` decodes to a coherent 2 × 2 atlas — an "Ear protectors must be
worn in this area" safety sign, a chest X-ray, a "RESTROOM" sign with an accessibility pictogram, and a colour chart. A wrong
offset or a wrong channel order does not produce readable signage; it produces noise. This is content, from the four packages
`umodel` refused.

**What is still unread**: the exports without `USize`/`VSize` in their properties — `M07_goldref` is one (a single `Palette`
property and 65,604 bytes of data). Their size is inherited from somewhere this tool does not model, and the same rule
applies as everywhere else on this page: a guessed size produces a plausible-looking image that is wrong.

#### The format-less textures, and an honest census of what remains

`Format` is absent on a minority of textures, and skipping them just because the property is missing is a rule about the
tool rather than about the data. The offset is **self-validating**, so the tool now uses it: at `+16`, byte 3 is the alpha
channel and is 255 almost everywhere. A texture is accepted when that holds for at least 90% of up to 20,000 sampled pixels,
and rejected otherwise.

That gained **2 textures and rejected 1**: `M07_fx_symbol_04` and `M07_fx_symbol_03` now decode, and one 64 × 64 export whose
alpha validates only **808 of 4,096** was refused — which is the guard doing its job rather than a loss.

**Verified by eye again**: `M07_fx_symbol_04.png` is a 64 × 64 cyan line-art glyph of an ibis-headed bird on black — an
Egyptian-style symbol, clean edges, correct colour. Not noise.

| outcome | count |
|---|---|
| PNG written | **51** |
| skipped — the object states no `USize`/`VSize` | 3,589 |
| skipped — the stated size does not fit 4 bytes/pixel | 771 |
| skipped — alpha does not validate at `+16` | 1 |

The 771 are the paletted and compressed formats: their payloads are smaller than `USize × VSize × 4`, which is the arithmetic
that says so. The 3,589 need the size from wherever the class inherits it — `M07_goldref` is one, with a single `Palette`
property and 65,604 bytes. Both groups are named here rather than approximated in the tool.

#### The exports that did not fit four bytes per pixel are mip chains

The 771 "truncated" exports are not malformed. Sampling the first 60 packages gives the shape:

| outcome | count |
|---|---|
| payload fits `USize × VSize × 4` | 15 |
| payload fits a **mip chain at one byte per pixel** | **127** |
| fits neither | 14 |

The declared formats among those that do not fit are **7** (20), **8** (99), **3** (14) and absent (8) — the compressed
family, not the BGRA one.

**The arithmetic is exact.** `Asgard/aluminium`, 512 × 512, format 8, has 349,681 bytes after the 16-byte header. The mip sum
`262,144 + 65,536 + 16,384 + 4,096 + 1,024 + 256 + 64 + 16 + 4 + 1` is **349,525**. A 256 × 256 format-7 texture: 87,520
available against a mip sum of **87,381**. Both leave a small constant-ish slack after the levels, which is the per-level
bookkeeping this project has not decoded yet — but the *chain* is unmistakable: every level from full size down to a single
pixel, one byte per pixel.

**So the next step is a mip-chain walker plus a block decoder**, not a size heuristic. Writing one that assumes "the first
`USize × VSize` bytes are the image" would silently read a compressed block stream as pixels and produce a picture that looks
like television static — which is exactly the outcome this page keeps insisting on avoiding.

Two smaller facts worth keeping:

- The **palettes exist in these same packages** (13 per `M07_fresco_tex`, 12 in `Tutorial_Tex`) and are not used by the
  four-byte textures at all — which is evidence that a paletted path exists somewhere in this data, most likely among the
  3,589 exports that state no size.
