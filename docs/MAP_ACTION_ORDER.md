# The order inside an `Actions` array (PLAN 5.2)

`inventory/action_order.csv` is one committed row per `.unr`, one per sequence class that carries an `Actions`
array in a map, one per class whose body states a rule about the walk, and a corpus census row. It is generated by
`tools/action-order.py` (`make action-order`), which reads each sequence class's own shipped `ScriptText` for the
rule and each map's `Actions` payloads for the order.

`docs/MAP_ACTION_WIRING.md` decoded the array as a count followed by that many compact export indices, and left
one thing open in its own words: *which end of the order runs first* -- "a per-element order is a T3D-level read,
not a census". `docs/MAP_EVENT_TARGETS.md` then measured which sequences a placed event name arms, and left the
rest on "a start the package does not carry". Both are answerable from text the packages already ship, and this
page is that read: the walk is four lines of the build's own UnrealScript, so the order is known before any
element is measured, and what the maps add is how far down that order each array actually gets.

## The walk, and the five classes that override it

The order is not inferred from the byte stream. Every class in this build carries its own source as a
`TextBuffer` export (`docs/PACKAGE_SCRIPT_TEXT.md`), and the sequence classes state their loop:

* `ScriptedSequence.SetActions` reads `Actions[C.ActionNum]`, and `C.ActionNum` is the only thing that selects an
  element -- there is no separate order property, no `Next` field, and no sort;
* `ScriptedTriggerController.InitializeFor` sets `ActionNum = 0` and calls `SetActions`, so a trigger's run starts
  at index 0 when the level starts (its own `PostBeginPlay` spawns that controller);
* `ScriptedAction.ProceedToNextAction` is `C.ActionNum += 1`, so the default is index 0, then 1, then 2.

Five classes replace that increment, and each says so in its own body: `ACTION_GotoAction` (an absolute
`ActionNumber`), `ACTION_EndSection` (a loop back to the section's start while an iteration counter runs),
`ACTION_IfCondition`, `ACTION_IfProximity` and `ACTION_IfRandomPct` (fall through, or call `ProceedToSectionEnd`,
which walks forward counting `StartsSection` / `EndsSection` and stops where the nesting goes negative). A sixth
class does not move the counter at all: `ACTION_LeaveSequence.GetScript` answers `None`, which ends the run where
it stands.

Because the rules are class bodies and the elements are class names, the whole thing is a static read: an array
is a short program, and its order is the array's own.

## The gate is a class table, not a placement field

`ScriptedTrigger.ValidAction` overrides the base's `return true` with `Actions[N].bValidForTrigger`, so a trigger
refuses an element by the element's *class* default. `ScriptedAction` states that default as true and twenty-one
classes in the family state it false -- both halves are read off the classes' `defaultproperties` blocks, so the
refusal set is a committed fact about the build rather than a guess about a placement. `SetActions`' answer to a
refused element is not to skip it: it warns `NOT VALID`, clears the current action and returns, so the run stops
there. A sequence that is not a trigger has no `ValidAction` override and runs whatever its array names.

## Where the starts come from

`TeamScriptedSequence` extends `UnrealScriptedSequence` extends `ScriptedSequence`, so the 8,716 actions its arrays
wire are ordered by the same walk -- but nothing a map's placed data fires has to arm it. Its start is a
`TakeOver(Pawn)`: `UnrealScriptedSequence.Trigger` calls it when a pawn triggers the sequence, and so does
`ScriptedSequence.SpawnControllerFor`. What a map's placed data provides instead is the *selection*: `priority`,
`TeamGoalType`, `bRoamingScript`, and a same-tag `NextScript` chain built in `BeginPlay` over every
`UnrealScriptedSequence` carrying the same `Tag`. The tag is a key the AI searches by, not an event name, which is
why counting fired names finds no start for these arrays -- and why "unarmed" was the wrong reading of them.
A `ScriptedTrigger` needs no name at all: its controller is spawned by its own `PostBeginPlay` and the run begins
with the level.

## Reading a row

`kind=map` rows carry per-map counts of arrays, slots, reach, gotos, section balance and gate refusals;
`kind=holder` rows are the same counts per sequence class, with the scene manager kept apart (`(scene manager)`,
257 arrays of `MatAction` camera elements, which are not scripted actions and are not part of the walk);
`kind=class` rows are the rules themselves -- which classes move the counter, open or close a section, end the
run, and what `bValidForTrigger` a class states (`note` carries `gate_value` and the ancestor it was inherited
from); `kind=census` is the corpus total.

`reach` counts the slots a straight run down the index gets through: the first slot that ends the run is included
(it is reached, then ends it) and nothing past it is. A run ends at a `None` slot (`SetActions` checks
`Actions[N] == None` and returns), at a `LeaveSequence`, at an element a gating class refuses, or at a
`GotoAction` whose `ActionNumber` is past the array. An in-range goto is not a cut -- it is a jump, so `reach` is
an upper bound on what runs where a goto jumps forward, and a lower bound where one jumps back.

## What this does not claim

* **A schedule.** `reach` is the order and the cuts, not a trace: `ACTION_IfCondition` and `ACTION_IfProximity`
  decide at run time, so which side of a section a given play takes is not in the package. What is in the package
  is the set of paths the classes allow.
* **That a refused element is dead content.** A trigger that stops at a refused class may be stopped on purpose --
  the warning is a diagnostic, not a crash. The count says how often the build would take that branch, not whether
  the branch is a bug.
* **A per-placement target for the 377 gotos that state none.** Their class declares `ActionNumber` and its
  defaults block names only `ActionString`, so the field keeps the type's zero and the jump goes to index 0. That
  is the loop the class's own comment warns about; whether any particular one was meant to be filled in is not
  something a package can say.
